Why this exists

Four things change once a skill is written down instead of living in one engineer's head.

The same judgment, every assistant

Whichever tool someone opens — Copilot in VS Code, Claude Code, Genie — it reads the same file and reasons the same way. No more "Copilot did something different than Claude did."

Nothing changes without a human

Every skill in this library is read-only by default. Two separate confirmations stand between a diagnosis and an actual change reaching production.

Minutes, not a support ticket

A failed job that used to mean paging someone and waiting can get a structured root-cause read in about the time it takes to read this paragraph twice.

Knowledge that compounds

Each new skill file is a written-down decision your best engineer already made once. The next person — or the next assistant — doesn't have to make it again.

What a skill file is

A written playbook an AI assistant reads before it acts — a job description precise enough that any assistant can actually follow it to the letter.

It's a text file, not software. Anyone on the team can open it and read exactly what the assistant is supposed to do — no reverse-engineering a plugin.

It lives in your repo, next to the code it's meant to help with — versioned, reviewed, and diffed like everything else.

Any assistant that can read a file can use it. That's the whole portability story — no per-platform rebuild.

It states boundaries as clearly as instructions — what the assistant is allowed to look at, and what it must never touch without asking first.

--- name: jobfix-agent description: Diagnoses a failed or anomalous Databricks pipeline from a run_id, a {job_name, date}, or a {dataset, date, metric} signal by mapping the failed job's neighborhood, forming a hypothesis, gathering only the read-only evidence needed to test it, and returning a structured verdict. ---

How it works, step by step

This is the actual sequence a skill like jobfix-agent follows — not a marketing simplification of it.

01

A signal arrives

A run_id, a job name and date, or a dataset that looks wrong — from a person or an upstream alert.

02

The assistant loads the matching skill

Only the one file that applies — read fresh at the start of the task, not baked in ahead of time.

03

It reads the real evidence

Logs, schema history, run history — never more than the current hypothesis actually calls for.

04

It tests its own theory

Up to three rounds, revising the hypothesis each time the evidence doesn't hold up.

05

It hands back one verdict

One of five structured outcomes — never a guess dressed up as certainty.

Worth knowing: how many tool calls that takes, and how many evidence rounds it needs, depends entirely on how tangled the failure is. A clean one-line fix might resolve in two calls; a failure that traces through three chained jobs might take a dozen. The steps above are the shape of the process, not a fixed step count.

Running it under observation: Omnigent

jobfix-agent doesn't need an IDE at all. It also runs as a governed agent inside Omnigent, an open-source meta-harness built by the Databricks AI team and Neon that wraps Claude Code, Codex, Cursor, and custom agents in one observable, policy-controlled session.

Runs as-is, no rewrite

A skill like this one drops straight into Omnigent as a custom YAML agent — same file, same reasoning, same verdicts.

The same two-gate model, now observable

Omnigent's policy layer can pause for human approval before risky actions and cap spend per session — the same "ask before touching anything live" discipline this skill already enforces, now visible and logged at the meta-harness level, not just inside the skill's own prompt.

Meet the first skill in the library

jobfix-agent

LIVE

Diagnoses a failed or anomalous Databricks pipeline from a run_id, a job name and date, or a dataset that looks wrong. It maps what sits upstream and downstream of the failure, forms one specific theory about the root cause, tests it against real evidence, and hands back a structured verdict — never a fix it applies on its own.

FIX_RECOMMENDED VERIFICATION_STEP_PROVIDED NOT_A_CODE_ISSUE OBSERVABILITY_GAP OUT_OF_SCOPE

Scope

Databricks only — Jobs API, SQL warehouse, notebook source, schema history, cluster events. No Airflow, no Kubernetes, no cloud storage access.

Safety model

Read-only by default. Implementing a fix needs explicit confirmation; applying it and rerunning the job needs a second, separate one.

Honesty by design

If evidence can't confirm a theory, it says so — VERIFICATION_STEP_PROVIDED, not a forced fix.

Full text lives at skills/jobfix-agent/SKILL.md in the repo.

What it will never do without asking you

These aren't defaults that happen to be safe today. They're constraints written into the skill file itself.

Never writes to, deletes, or reruns anything by default — every action reaching a verdict is read-only.

Two separate, explicit confirmations stand between a diagnosis and a live notebook actually changing.

Never invents confidence — says "I can't verify this" instead of forcing a fix it isn't sure about.

Never edits or reruns an upstream job, even when that job is confirmed to be the actual root cause.

Stays inside its stated scope — no Airflow, no Kubernetes, no cloud object storage access, ever.

Set up jobfix-agent in VS Code

Three things have to be true before an assistant can actually run this skill: VS Code can reach your Databricks workspace, your assistant has the skill file in its context, and you've confirmed it loaded correctly.

A

Connect VS Code to your Databricks workspace

Two supported ways to do this — use whichever your team already standardizes on.

Databricks extension (recommended for most people)

Install the official Databricks extension from the VS Code marketplace → Command Palette → Databricks: Configure workspace → paste your workspace URL → sign in via OAuth (browser) or a personal access token → pick the default cluster or SQL warehouse.

Databricks CLI profile (what the skill's own tool calls run on)

Install the CLI, then run databricks auth login (OAuth) or databricks configure --token against your workspace URL. This writes a profile to ~/.databrickscfg — the same credentials the PowerShell + Python SDK client reads from when the skill actually calls the Jobs and Workspace APIs. Verify with databricks workspace list /.

B

Add SKILL.md to your assistant's context

How you do this depends on which assistant you're running inside VS Code:

Claude Code — drop the folder at .claude/skills/jobfix-agent/SKILL.md in your project. It's indexed and triggered automatically; nothing to reference by hand each time.

GitHub Copilot — either point at it directly in chat ("Follow skills/jobfix-agent/SKILL.md to diagnose this run"), or add a reference to it in your repo's .github/copilot-instructions.md so it's pulled in automatically.

Genie / other Databricks-native assistants — attach the file to the space, or paste its contents into space instructions. Setup varies by workspace — check with your admin if you're not sure how your space ingests files.

C

Confirm it actually loaded

Ask your assistant: "What tools do you have available to resolve a failed Databricks job, and what does the jobfix-agent skill say your output format must be?" If it answers both parts accurately — naming the Jobs and Workspace API calls and the five-verdict output contract — it's wired up correctly. If it can't, re-check step B before assuming the skill itself is at fault.

Questions people actually ask

Will this change our production systems on its own? +

No. Every skill in this library is read-only by default. A recommendation is never the same thing as a change — implementing and rerunning each require their own explicit, unambiguous confirmation from a person.

What happens if the AI isn't confident? +

It says so. A skill like jobfix-agent will return VERIFICATION_STEP_PROVIDED rather than force a fix — you get the specific thing to check, not a guess dressed up as certainty.

Does this replace our engineers? +

No — it removes the repetitive first pass of evidence-gathering so an engineer's time goes to judgment calls, not log-scrolling. A human still decides what actually ships.

What if we use an AI assistant that isn't listed? +

If it can read a text file and call tools against your systems, it can very likely use these skills — the format has no dependency on any one vendor. Worth a quick test before relying on it.

Where do these skill files actually live? +

In your team's own git repository, versioned and reviewed like any other code — never inside a proprietary tool you'd lose access to.
